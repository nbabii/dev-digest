# Blast Radius (PR Overview card + MCP `get_blast_radius`)

## Goal
Show a reviewer what else in the repo a PR can affect: the symbols whose declared line range the PR's diff actually touches (decision 12; user decision 2026-10-03, not every symbol of a changed file), who calls them, and which HTTP endpoints and crons may depend on those callers. The map is rendered as a "Blast radius" card on the PR Overview tab and returned by the MCP tool `get_blast_radius`. Both read the same new server endpoint, so Claude Code and the browser give the same answer. The feature only **reads** data that `repo-intel` already indexed. It never re-analyzes the repo and never calls an LLM.

## Non-goals
- No LLM call, no embedding, no `git clone`/`fetch`, no AST parsing or ripgrep on the request path. Always serve from Postgres. The facade's ripgrep fallback is **explicitly not used** (decision 3).
- No re-indexing triggered by a read. (One explicit user-initiated "Re-analyze" button reuses the existing `POST /repos/:id/resync`; it can be dropped, see open questions.)
- No transitive blast (importers of importers), no re-parsing of PR head files to find symbols the PR adds (added symbols are not in the index; they surface as `uncovered`), no GHE/non-github.com links (the client helper is also github.com only), no new DB table or column.
- No PR Brief composition (`PrBrief.blast` stays as is).

## Architecture decisions
1. **New `server/src/modules/blast/` module, not routes inside `repo-intel` or `reviews`.** `repo-intel` is PR-agnostic and tenant-agnostic by design (`routes.ts:36-38`); resolving a PR's changed files and workspace scoping is a PR concern. `reviews` already owns Intent and run execution, and a read-only impact map would only add weight there. `modules/index.ts` already anticipates a `blast` module. Layout (`onion-architecture`: direction, not folders): `routes.ts` (delivery), `service.ts` (application, `BlastService(container)`), `repository.ts` (pull, repo and `pr_files` lookups returning purpose-shaped types), `helpers.ts` (pure: grouping, caps, cron/URL formatting), `constants.ts`. The service imports **no** file from `modules/reviews/*` (no lateral reach) and uses only `container.repoIntel`, `container.git`, `container.github()` and `container.config`. Type imports from `modules/repo-intel/types.ts` (the port's types) are fine.
2. **Endpoint: `GET /pulls/:id/blast-radius`** (PR uuid, `IdParams`, `getContext` workspace scoping). Every PR-scoped read in this repo is `/pulls/:id/...` (`/pulls/:id/intent`, `/reviews`, `/runs`), the page already holds `prId`, and the MCP `resolver.pull(repoId, number)` already yields that uuid. `/repos/:id/pulls/:number/...` exists nowhere. 404 `NotFoundError('Pull request not found')` for an unknown PR. Default rate limit only (cheap DB reads).
3. **Persistent index only, never the ripgrep fallback.** `RepoIntelService.getBlastRadius` silently falls back to reading the clone (`service.ts:228-304`), which violates "no re-analysis". `BlastService` therefore first calls `getIndexState`. It calls `getBlastRadius` only when the state is `full` or `partial`. If the result still comes back `degraded` (a race), it is treated as not available. Other states return an empty, honestly labelled report.
4. **Changed files and their patches from ready data, in three tiers**: (a) `pr_files` rows (`path` + `patch`), (b) `container.git.diff(base, head)` on the existing clone (already returns parsed hunks; same call as `diff-loader.ts`), (c) best-effort `container.github().getPullRequest` file list with its `patch` fields, **only if** (a) and (b) are empty (a PR never opened in the UI, which is the normal MCP-first case). Tier (c) is read-only and not persisted. The response reports which tier was used (`changed_files.source`). Patches are needed because symbol selection is hunk-based (decision 12); a file whose patch is missing (binary, GitHub-truncated large patch, tier without patch text) falls back per file as described there. Open question 3 covers whether to keep tier (c).
5. **Index state is two orthogonal fields**, not one enum: `status` (`ready | partial | degraded | not_indexed | disabled`) and `indexing: boolean`. A refresh or resync in flight on a repo that already has a usable index should still show data (with a "re-indexing" banner). Derivation lives in a pure helper `deriveIndex(...)`:
   - flag off gives `disabled`.
   - no `repo_index_state` row gives `not_indexed`.
   - `full` gives `ready`; `partial` gives `partial`; `degraded|failed` gives `degraded`.
   - `available = status in {ready, partial}`.
   - `facts_complete = false` when a partial index stopped on `soft_budget` or `graph_failed` (see below).
   - `indexing` comes from a new additive `IndexState.indexing?` field (task: facade).
   Two facts from the pipeline shape this: on `soft_budget` `file_facts` is **never written** (`full.ts:246-248` is inside `if (!softBudgetReached)`), and on `graph_failed` there are no `file_edges`, so `decl_file` never resolves and callers are empty. A partial index with zero callers and zero endpoints must therefore **not** claim "no callers"; the UI says "index incomplete". The pipeline stores these flags in `stats` (`softBudgetReached`, `graphFailed`) but not in `stats.reason`, which is what `tryGetIndexState` reads (`repository.ts:214`). The facade task projects them into `reason`.
6. **Contract: reuse `BlastCaller` and `DownstreamImpact`, add a new `BlastRadiusReport`; leave `BlastRadius` and `PrBrief` untouched.** Changing `BlastRadius` would break `server/test/contracts.test.ts:79-92` and the future `PrBrief` composition. The report is a superset that can later be mapped to `BlastRadius` with a pure function. Shape (see Tasks for the exact zod):
   - `repo` (`owner/name`), `pr_id`, `pr_number`.
   - `index {status, indexing, available, reason, facts_complete, last_indexed_sha, indexed_at}`.
   - `changed_files {total, covered, uncovered[], source, truncated}`.
   - `totals {symbols, callers, endpoints, crons}`. These are **distinct counts computed before any cap** and are the only numbers consumers may display (rule: consumers never recompute totals).
   - `symbols[]` = `DownstreamImpact.extend({file, kind, line, exported, callers: BlastCaller+url[], callers_total, endpoints_total, crons_total})`.
   - `limits {symbols_truncated, callers_truncated}`.
7. **Grouping and attribution, all from existing rows:**
   - Candidate symbols = `getSymbolsInFiles(repoId, changedFiles)` (gives `startLine`/`endLine`, `exported`, and the `covered` file set) minus dotted `Class.method` duplicates, deduped by `(file, name)` (prefer the callable kind and the lowest line). **Changed symbols = the candidates the diff touches**, selected by `selectTouchedSymbols` (decision 12). Only touched symbols are counted, listed, and looked up for callers.
   - Callers per symbol = `getBlastRadius(...).callers` grouped by `(declFile, viaSymbol)`. The facade needs an additive `declFile` on caller rows, because grouping by name alone would mix two changed files that each declare e.g. `init`. Callers are resolved references only (`decl_file` set, precise), already deduped per `(file, enclosing symbol, symbol)`. `BlastCaller.name` is the enclosing symbol.
   - Endpoints and crons per symbol = union of `factsByFile[callerFile]` over **all** of that symbol's callers (pre-cap), then formatted, deduped, sorted. This is an over-approximation ("may depend"): a caller file's facts are attributed to every symbol it calls. UI copy must say "may". Open question 5 covers also including the changed file's own facts.
   - Cron label: `job:<kind>` gives `<kind>`; an expression gives `<basename of the caller file without extension> (<hourly|daily|weekly|monthly|every N min|every N h|raw expr>)`, e.g. `reset-buckets (hourly)`, which matches the mockup. The name is a heuristic (the index stores no job name); open question 4.
   - Caps (constants in `blast/constants.ts`): `MAX_SYMBOLS = 30`, `MAX_CALLERS_PER_SYMBOL = 20` (same value as the facade's `MAX_CALLERS_PER_SYMBOL`, which is today wrongly applied as a global `slice` at `service.ts:386`), `MAX_ENDPOINTS_PER_SYMBOL = 25`, `MAX_CRONS_PER_SYMBOL = 10`, `MAX_UNCOVERED_LISTED = 20`, `MAX_CHANGED_FILES = 1000` (the `inArray` bound; sets `changed_files.truncated`). The facade gets a SQL hard cap of 5000 caller rows so a hub symbol cannot flood memory.
   - Sorting (deterministic, so UI == MCP): symbols by `match` (`hunk` before `file`), then `callers_total` desc, exported first, file, line, name. Callers by file rank desc (facade), then file, then line. Endpoints and crons alphabetical.
8. **GitHub links are built once, on the server.** Each caller carries `url = https://github.com/{full_name}/blob/{ref}/{encoded path}#L{line}`. `ref` is `index.last_indexed_sha` (fallback: repo `default_branch`), **not** the PR head sha: caller line numbers come from the indexed default-branch snapshot, and a PR head would point at shifted lines. Path segments are `encodeURIComponent`-ed (file names are attacker-influenced). Building it server-side lets the MCP tool print real links without importing `client/src/lib/github-urls.ts`, and keeps UI and MCP identical. The client renders the URL only as `<a href>` with `target="_blank" rel="noopener noreferrer"`.
9. **UI: Tree is mandatory; Graph is a stretch task and v1 ships no toggle.** Reasons: no user story needs Graph; it needs an SVG layout (or `mermaid`, which fights theming); the mockup's edges are caller to endpoint, which needs **per-caller** endpoint attribution that the v1 contract does not carry (it aggregates per symbol, to keep MCP tokens small); and a visual-only graph needs a text alternative anyway, which is the Tree. Do not ship a dead "Graph" button. The stretch task adds optional `endpoints`/`crons` per caller (additive) and then the view.
10. **MCP: same endpoint, same data; follow the package conventions rather than invent a new format.** `response_format` stays `concise | detailed` (existing `responseFormat` in `tools/schemas.ts`), with `structuredContent` plus a one-line `content` text (`mcp-server` plan decision 12 forbids a JSON copy in `content`). Both formats contain **every** symbol and caller the API returned; `detailed` only adds caller names, URLs and the `exported`/`line` fields. Open question 1 covers whether the user wants a rendered markdown tree in `content` instead.
11. **No recompute rule.** The UI summary row and the MCP summary line read `totals` and `*_total` from the response, never sums of the arrays (arrays are capped). One acceptance test enforces this with a deliberately inconsistent fixture.
12. **Symbols = only those the diff touches (hunk intersection), per user decision 2026-10-03.** All inputs already exist: `symbols.line`/`end_line` from the index, and patches from decision 4. Coordinates: the index is a default-branch snapshot, i.e. the PR's **base** side, so matching uses the **old-side (`-`) line numbers** of each hunk, never new-side numbers.
   - Pure helper `touchedBaseLines(patch) -> { lines: Set<number>, insertions: number[] }` in `blast/helpers.ts`. It walks the patch text with an old-line cursor from each `@@ -oldStart,oldLines ... @@` header: a `-` line adds the cursor to `lines` and advances; a ` ` context line only advances; a `+` line records an insertion boundary `k` = the last old line before it (once per run of `+` lines). It reuses no hunk object from `parseUnifiedDiff` because `DiffHunk` keeps only new-side numbers; for tier (b) the helper runs on the raw per-file patch text the git adapter already has, or the adapter result is re-serialized the same way `diffFromPrFiles` does (implementer picks whichever needs no adapter change; document it).
   - Pure helper `selectTouchedSymbols(candidates, touchedByFile)`: a symbol `S` with range `[start, end]` is touched when (i) some removed/modified line is in `[start, end]`, or (ii) some insertion boundary `k` satisfies `start <= k < end` (an insertion strictly inside the body; lines appended right after a function's last line do not touch it). Nested symbols are each tested on their own (a method edit also matches its enclosing class; both kept, since callers of the class are affected too). Context lines never count.
   - Per-file fallback, `match: 'file'`: when a changed file is covered by the index but has **no patch** (binary, GitHub-truncated, or no patch text in the tier) or its symbols have **no usable range** (`end_line` null for every symbol, from an older index), all of its candidate symbols are included and marked `match: 'file'`. Everything selected by intersection is `match: 'hunk'`. This keeps the map from silently dropping impact when precision is impossible.
   - A deleted file has every old line removed, so all its symbols match naturally. An added file is not in the index and stays `uncovered`.
   - A covered file whose hunks touch **no** symbol (imports, top-level config, comments between functions) goes to `changed_files.no_symbol_touched` so the UI can say why it contributes nothing, instead of hiding it.
   - Alignment caveat: when the default branch moved after the PR's merge-base, indexed ranges can be shifted relative to the patch's old-side numbers. `pull_requests` stores only the `base` branch name (no base sha), so this cannot be detected exactly; it is surfaced through the existing snapshot footnote (`last_indexed_sha`, `indexed_at`) and listed under Risks. No re-analysis is done to correct it.

## Risks / open questions
- **Cron fidelity (gap, decision made, please confirm).** The index stores only a cron expression or `job:<kind>` (`extract.ts:202-214`), not a name or schedule text. The mockup's `reset-rate-buckets (hourly)` is reproduced by deriving the name from the file basename and humanizing the expression. This is a heuristic and `extractCrons` can false-positive (its job-kind branch triggers on any line containing "job", "sync", "index"...). Re-extracting with better names would be re-analysis and is out of scope.
- **Endpoint and cron attribution is an over-approximation.** Facts are per caller **file**, attributed to every symbol the file calls. Fastify route prefixes registered via `register(..., {prefix})` are not resolved, so endpoint paths can be partial. Direct callers only (no transitive importers). UI copy says "may depend".
- **Index freshness vs PR head.** The index is the default-branch snapshot at `last_indexed_sha` (it is refreshed on resync/poll, never per PR). Symbols and files **added** by the PR are not in it (`changed_files.uncovered`), and line numbers refer to that snapshot, hence links use the indexed sha. A stale index shows stale callers. The footnote and `indexed_at` make this visible; the index is not auto-refreshed on read.
- **Hunk-intersection precision (decided: only symbols the diff touches).** Ranges come from the indexed default-branch snapshot and are matched against the patch's old-side lines. If the default branch moved in that file after the PR's merge-base, ranges can be off and a touched symbol can be missed or a neighbour matched; there is no base sha in `pull_requests` to detect it. Mitigations: snapshot footnote, `match:'file'` fallback when no patch/range exists, `no_symbol_touched` list so dropped files are visible. A changed **signature line** counts as touching (it is inside `[start, end]`). Changes to module-level code that a symbol reads (e.g. a top-level constant without its own symbol row) are not attributed to that symbol; such files appear under `no_symbol_touched`. Non-exported touched symbols can never have resolved callers (`resolveReferences` links exported symbols only, `repository.ts:406-424`), so they show "0 callers".
- **Index race while indexing.** Full/incremental indexing is delete-then-insert and not one transaction (`full.ts:204-206`), so a read during a refresh can see partial data. We show a banner when `indexing` is true.
- **Large repos / hub symbols.** Mitigated by the SQL row cap (5000), per-symbol caps, `MAX_CHANGED_FILES`, and `MAX_SYMBOLS`. `callers_total` is exact only below the row cap (`limits.callers_truncated` marks it). Not load-tested.
- **Uncovered languages.** `SUPPORTED_EXT` is TS/JS only (`constants.ts:14`). A Python or Go PR shows "no indexed symbols"; the notice must say the language is not indexed, not "no impact".
- **Never-opened PR in MCP.** Depends on the 3-tier changed-file resolution; tier (c) uses a GitHub call (needs a token; otherwise `changed_files.source = "none"` and the tool hints "open the PR once in DevDigest").
- **MCP `listPulls` side effect** (it syncs GitHub, `mcp-server/CLAUDE.md`) applies here too through `resolver.pull`; unchanged behaviour.
- **Seeding the demo index (decided 2026-10-03: seed by default, no flag).** It changes what the review engine reads for the demo repo: `getCallerSignatures` (`run-executor.ts:482`) adds a callers section to PR #482 review prompts (accepted), `buildRankNote` (`:530-547`) stays silent because percentiles are < 95, the repo map stays empty. Residual risk: an existing test or e2e flow that implicitly relied on the empty index; covered by the pre-check in the seed task. A seed flag is no longer the fallback; a broken test is fixed in place and reported.
- **Security.** Workspace scoping comes from `getPull(workspaceId, ...)` (repo-intel tables are keyed by `repoId` only, with no `workspace_id`, so the PR lookup is the tenancy gate). The URL is built from DB values and encoded segments. Symbol and file names are untrusted in MCP output; the description says so. No secrets or file contents are logged.
- **Contract hand-sync.** `server/src/vendor/...` and `client/src/vendor/...` copies are maintained by hand (no sync script exists). The `diff` check in the acceptance list is the only guard.
- **Open questions that need your decision:**
  1. MCP output format: the repo convention is `response_format = concise|detailed` with `structuredContent` and a one-line text. You wrote "markdown/json". Default in this plan: keep the convention. Alternative: add a `markdown` value that returns the rendered Tree in `content` (helps clients that ignore `structuredContent`, but breaks the "no JSON/text duplicate" rule for this tool and costs tokens).
  2. ~~Symbol scope~~ **Decided 2026-10-03: only symbols whose indexed line range the diff touches (decision 12), with a per-file `match:'file'` fallback.**

  6. Is the explicit "Re-analyze" button (reuses `POST /repos/:id/resync`) acceptable given "no re-indexing"? Default: yes, as a user-initiated click only.
