## Decisions

- **2026-09-16** — For the PR-list per-severity Findings column, chose one extra read-time aggregation query (`findings ⋈ reviews`, grouped in JS — same pattern as the existing score/cost lookups) over denormalized `critical_count`/`warning_count`/`suggestion_count` columns on `agent_runs`. Avoids keeping counters in sync on finding accept/dismiss and a migration; a prior attempt at the denormalized approach was already tried and reverted (see the `pnpm db:migrate` entry below, 2026-09-15) (`server/src/modules/pulls/routes.ts`, `server/specs/findings-counter.md`).
- **2026-09-20** — Skills feature's Trust model (`server/specs/skills.md`) requires `POST /skills` to always persist `source:'manual'` and `POST /skills/import` to only ever produce `source` in `{'imported_url','extracted'}` with `enabled` always forced `false`. Enforced this entirely at the Zod route-schema layer rather than in the service: `CreateSkillBody` (`server/src/modules/skills/routes.ts`) has no `source` field at all (any client-sent value is stripped before the service ever sees it), and `ConfirmImportBody`'s `source` is `z.enum(['imported_url','extracted'])` — excludes `'manual'`/`'community'` at validation time (422), not by convention. Chosen over service-level validation because it fails fast and can't be bypassed by a future call site that forgets to re-check.
- **2026-09-20** — `RunTrace.prompt_assembly.token_counts.skills` (new optional field on `PromptAssembly`, `server/src/vendor/shared/contracts/trace.ts`) is computed inline in `ReviewRunExecutor.runOneAgent`, NOT in `platform/trace-builder.ts`'s `buildRunTrace()` — that helper is a separate path used only by the A5 multi-agent/built-in-detector flow and doesn't share trace construction with the per-agent review run (`server/src/modules/reviews/run-executor.ts`).
- **2026-09-20** — `server/specs/skills.md` described `VersionParams` (`{id: uuid, version: positive int}`) as already living in `modules/_shared/schemas.ts` alongside `IdParams`; it didn't — it was defined locally inside `modules/agents/routes.ts`. Moved it into `_shared/schemas.ts` and updated `agents/routes.ts` to import it from there, since `skills/routes.ts` needed the identical schema for `GET /skills/:id/versions/:version`. Small correction to the spec's stated premise, done to avoid duplicating the same schema in two route files.

## Recurring Errors & Fixes

- **2026-09-15** — `pnpm db:migrate` fails with `column "X" of relation "Y" already exists` even on a freshly `git reset` starter tree: the local Postgres volume (`devdigest_pgdata`) is never wiped by a git revert, so it can still carry schema/data from previously-merged-then-reverted branches (e.g. `agent_runs.cost_usd` and unrelated leftover columns `critical_count`/`warning_count`/`suggestion_count` were already physically present before this session's migration re-added `cost_usd`). Before running `db:migrate` after picking up schema work, check the live DB first: `docker exec devdigest-postgres psql -U devdigest -d devdigest -c '\d <table>'` and `select * from drizzle.__drizzle_migrations`. If a column already exists and matches the intended schema, don't re-run the ALTER — baseline the generated migration as applied instead: `sha256` the migration `.sql` file (matches `drizzle-orm/postgres-js/migrator`'s `readMigrationFiles`, which hashes the raw file content) and `INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('<sha256>', <journal "when" ms>)` — no data touched, journal reconciled with physical reality (`server/src/db/migrations/0010_superb_abomination.sql`).
- **2026-09-20** — `db.update(table).set({}).where(...)` throws `500 "No values to set"` (postgres-js/Drizzle) when every field in an update patch resolves to `undefined` — e.g. a Zod route-body schema silently strips an unknown/immutable field (like `source` on a skill), leaving an empty patch object. Hit via `PUT /skills/:id { source: 'community' }` alone: the schema strips `source` (immutable provenance), the patch becomes `{}`, and `SkillsRepository.update` called `.set({})` before this fix. Fixed there by returning the existing row unchanged when every patch field is `undefined`, before ever calling `.update().set()` (`server/src/modules/skills/repository.ts`). CONFIRMED the identical bug pre-exists in `AgentsRepository.update` (`server/src/modules/agents/repository.ts`) — a `PUT /agents/:id` body that fully strips to `{}` also 500s the same way. NOT fixed there in this session (out of scope for the Skills feature); the same guard would apply if picked up later.

## Codebase Patterns & Tool Notes

- **2026-09-16** — A `reviews` row (and its `findings`) is only ever persisted on the success path of `ReviewRunExecutor.executeRuns`, right before `completeAgentRun(runId, {status:'done',...})`; a failed/cancelled run hits the `catch` block instead and never inserts a `reviews` row at all. So any query that joins through `reviews` is already implicitly scoped to completed runs — no need to additionally join/filter on `agent_runs.status` (`server/src/modules/reviews/run-executor.ts:218-254,292-310`).
- **2026-09-20** — `fflate`'s `unzipSync(data, { filter })` calls the filter callback with just central-directory metadata (`name`, `size`, `originalSize`, `compression`) BEFORE deciding whether to inflate an entry — returning `false` guarantees that entry's bytes are never decompressed. Used in `server/src/modules/skills/import-parser.ts` to guarantee a zip's non-`.md`/`.txt` entries (scripts, binaries) are never read past their name/size, and to enforce a decompressed-byte-total cap (zip-bomb guard) and a total-entry-count cap purely from data the filter already receives, with no separate archive-walking pass needed.

## Open Questions

- **2026-09-16** — Root `CLAUDE.md`'s gotcha "`*/src/vendor/` (client, server) — vendored third-party code (`@devdigest/ui`, `@devdigest/shared`); patch upstream, not in place" groups `@devdigest/shared` with `@devdigest/ui`, but no upstream/source-of-truth for `@devdigest/shared` appears to exist anywhere in this repo or as an installed package — `server/src/vendor/shared/contracts/platform.ts` and `client/src/vendor/shared/contracts/platform.ts` are byte-identical (checked via `diff`) with no sync script or build step found. Adding a field to `PrMeta` this session meant hand-editing both copies directly, which is the only way it seems editable at all. Worth confirming whether "patch upstream" ever applied to the shared contracts specifically (vs. just `@devdigest/ui`, which has a "ported from findings.jsx" comment implying a real prior source), or whether the `CLAUDE.md` wording should be split.
