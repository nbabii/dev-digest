## Decisions

- **2026-09-16** — For the PR-list per-severity Findings column, chose one extra read-time aggregation query (`findings ⋈ reviews`, grouped in JS — same pattern as the existing score/cost lookups) over denormalized `critical_count`/`warning_count`/`suggestion_count` columns on `agent_runs`. Avoids keeping counters in sync on finding accept/dismiss and a migration; a prior attempt at the denormalized approach was already tried and reverted (see the `pnpm db:migrate` entry below, 2026-09-15) (`server/src/modules/pulls/routes.ts`, `server/specs/findings-counter.md`).
- **2026-09-20** — Skills feature's Trust model (`server/specs/skills.md`) requires `POST /skills` to always persist `source:'manual'` and `POST /skills/import` to only ever produce `source` in `{'imported_url','extracted'}` with `enabled` always forced `false`. Enforced this entirely at the Zod route-schema layer rather than in the service: `CreateSkillBody` (`server/src/modules/skills/routes.ts`) has no `source` field at all (any client-sent value is stripped before the service ever sees it), and `ConfirmImportBody`'s `source` is `z.enum(['imported_url','extracted'])` — excludes `'manual'`/`'community'` at validation time (422), not by convention. Chosen over service-level validation because it fails fast and can't be bypassed by a future call site that forgets to re-check.
- **2026-09-20** — `RunTrace.prompt_assembly.token_counts.skills` (new optional field on `PromptAssembly`, `server/src/vendor/shared/contracts/trace.ts`) is computed inline in `ReviewRunExecutor.runOneAgent`, NOT in `platform/trace-builder.ts`'s `buildRunTrace()` — that helper is a separate path used only by the A5 multi-agent/built-in-detector flow and doesn't share trace construction with the per-agent review run (`server/src/modules/reviews/run-executor.ts`).
- **2026-09-20** — `server/specs/skills.md` described `VersionParams` (`{id: uuid, version: positive int}`) as already living in `modules/_shared/schemas.ts` alongside `IdParams`; it didn't — it was defined locally inside `modules/agents/routes.ts`. Moved it into `_shared/schemas.ts` and updated `agents/routes.ts` to import it from there, since `skills/routes.ts` needed the identical schema for `GET /skills/:id/versions/:version`. Small correction to the spec's stated premise, done to avoid duplicating the same schema in two route files.
- **2026-09-20** — Conventions Extractor spec (`server/specs/conventions-extractor.md`) uses two new tables, `convention_scans` (run header: status/model/tokens/cost/error, mirrors `agent_runs`) + `conventions` (candidate rows, child), instead of one — a re-scan can fail or find zero candidates, and that outcome still needs a persisted, queryable trace (`status`, `error`) for "last scan Xh ago" without any candidate row to hang it off.
- **2026-09-20** — A `convention_scans` row stuck at `status: 'running'` (crashed/restarted process, or `JobRunner`'s 120s timeout giving up on a call that keeps running in the background — see the `JobRunner` unhandled-rejection entry above) has no path back to a terminal state, and `GET /repos/:id/conventions` always shows the LATEST scan — so the UI's "scanning…" spinner ran forever with no escape (reported live: a double-fired "Re-scan" click raced two scans for the same repo; the newer one got orphaned by a crash and the user was stuck watching it). Fixed with three additive pieces, all in `conventions/service.ts` + `conventions/repository.ts`: (1) `ConventionsService.reconcileIfStale` — a lazy check on every `GET`/`hasActiveScan` read, not a boot hook, so it also catches a same-process hang, not just a crash-restart — flips a `running` scan older than `SCAN_STALE_MS` (150s, above `JobRunner`'s own 120s timeout) to `failed, error:'stale_timeout'`; (2) `ConventionsService.hasActiveScan`, checked by `POST /repos/:id/conventions/extract` before enqueueing, refuses a second concurrent scan for the same repo (narrows the race, not a DB-level lock — accepted as sufficient for human-click frequency); (3) `ConventionsRepository.completeScan`/`failScan` both gained a `WHERE status = 'running'` guard, because the ORIGINAL orphaned job's `await llm.completeStructured(...)` doesn't actually get cancelled when `JobRunner`'s timeout gives up on it — without the guard, that call resolving/rejecting much later would silently overwrite the reconciliation's `failed` status with stale data. Confirmed live: a scan reconciled to `stale_timeout` via `GET` polling while its original job was still technically running in the background never got clobbered once that background call eventually settled.

## Recurring Errors & Fixes

- **2026-09-15** — `pnpm db:migrate` fails with `column "X" of relation "Y" already exists` even on a freshly `git reset` starter tree: the local Postgres volume (`devdigest_pgdata`) is never wiped by a git revert, so it can still carry schema/data from previously-merged-then-reverted branches (e.g. `agent_runs.cost_usd` and unrelated leftover columns `critical_count`/`warning_count`/`suggestion_count` were already physically present before this session's migration re-added `cost_usd`). Before running `db:migrate` after picking up schema work, check the live DB first: `docker exec devdigest-postgres psql -U devdigest -d devdigest -c '\d <table>'` and `select * from drizzle.__drizzle_migrations`. If a column already exists and matches the intended schema, don't re-run the ALTER — baseline the generated migration as applied instead: `sha256` the migration `.sql` file (matches `drizzle-orm/postgres-js/migrator`'s `readMigrationFiles`, which hashes the raw file content) and `INSERT INTO drizzle.__drizzle_migrations (hash, created_at) VALUES ('<sha256>', <journal "when" ms>)` — no data touched, journal reconciled with physical reality (`server/src/db/migrations/0010_superb_abomination.sql`).
- **2026-09-20** — `JobRunner.enqueue()`'s returned `{ done }` promise (`server/src/platform/jobs.ts`) rejects when the job handler fails/times out, but **every existing caller fire-and-forgets it** (`repos/service.ts`, `repo-intel/routes.ts`, and this session's new `conventions/routes.ts` all discard the `job` object or only read `job.id`) — nothing ever attaches a `.catch()`. In Node ≥15, an unhandled promise rejection terminates the process by default. Hit for real, twice, during manual testing: a conventions-extraction job that hit the 120s `JobRunner` timeout crashed the whole `tsx watch` API process (`TimeoutError: Operation timed out after 120000ms` at `resilience.ts:17`, then a bare `Node.js v22.17.0` crash with no further stack — that terse crash shape, not a normal error log, is the tell that it's an unhandled-rejection kill, not an application-level error). This affects **every** job kind (index/refresh/resync too), not just conventions — any slow/failing background job could crash the API process. Fixed generically in `JobRunner.enqueue()`: `done.catch(() => {})` right after constructing it marks the promise itself as handled (a caller can still attach its own `.catch()`on the same `done` — this no-op doesn't suppress that), so a job failure is only ever recorded via `jobs.status`/`error`, never a process crash. Regression-tested in `server/test/jobs.test.ts` (asserts no `process.on('unhandledRejection', ...)` fires for a handler that throws) — confirmed the test fails without the fix (real `[Error: boom]` unhandled rejection) and passes with it.
- **2026-09-20** — `db.update(table).set({}).where(...)` throws `500 "No values to set"` (postgres-js/Drizzle) when every field in an update patch resolves to `undefined` — e.g. a Zod route-body schema silently strips an unknown/immutable field (like `source` on a skill), leaving an empty patch object. Hit via `PUT /skills/:id { source: 'community' }` alone: the schema strips `source` (immutable provenance), the patch becomes `{}`, and `SkillsRepository.update` called `.set({})` before this fix. Fixed there by returning the existing row unchanged when every patch field is `undefined`, before ever calling `.update().set()` (`server/src/modules/skills/repository.ts`). CONFIRMED the identical bug pre-exists in `AgentsRepository.update` (`server/src/modules/agents/repository.ts`) — a `PUT /agents/:id` body that fully strips to `{}` also 500s the same way. NOT fixed there in this session (out of scope for the Skills feature); the same guard would apply if picked up later.

## Codebase Patterns & Tool Notes

- **2026-09-20** — `server/src/vendor/shared/contracts/platform.ts`'s `FEATURE_MODELS` registry already has a `'conventions'` entry (default `openai`/`gpt-5.4`) and `server/src/modules/settings/feature-models.ts` already implements `resolveFeatureModel`/`getFeatureModelOverride` for it — but `resolveFeatureModel(` has zero call sites anywhere in `server/src`. All five registered features (`onboarding`, `review_intent`, `risk_brief`, `conformance`, `conventions`) still read a hardcoded model constant in their own module; the Settings → Feature Models UI has nothing wired to it yet. When starting new feature work, check whether it's meant to be the first real consumer of one of these slots before hardcoding a model.
- **2026-09-20** — `RepoIntelService.getConventionSamples(repoId, n)` (`server/src/modules/repo-intel/service.ts:630-632`, thin wrapper over `getTopFilesByRank`) already implements "top-N ranked files, junk-path-filtered" sample selection with no caller anywhere yet — built ahead of the conventions-extraction feature it's evidently meant for (see `server/specs/conventions-extractor.md`).
- **2026-09-20** — `server/src/db/schema.ts`'s barrel-file header states an explicit repo-wide rule: "every domain table carries `workspace_id` (FK→workspaces)". Easy to miss if a new table is designed from a narrower nearby precedent instead (e.g. `repo-intel`'s own tables are keyed by `repo_id` only, no `workspace_id`) — always check the `schema.ts` barrel header, not just a sibling table, before finalizing a new table's columns.
- **2026-09-20** — A `conventions` table AND a `ConventionCandidate` Zod contract already exist (`server/src/db/schema/knowledge.ts:31-42`, `server/src/vendor/shared/contracts/knowledge.ts:146-154`, mirrored client-side) — already in the canonical `schema` object in `server/src/db/schema.ts` and already shipped in `0000_init.sql`, but with zero real callers anywhere (confirmed by grep). First draft of `server/specs/conventions-extractor.md` missed this entirely and designed a second, competing `conventions` table/type from scratch — caught only by an independent fact-check subagent reviewing the spec against the actual repo, not by the original research pass. Lesson: when a spec proposes a "new" table or exported type name, always grep for that exact name across the whole repo first (not just the module being worked in) — this codebase pre-seeds dead-but-real scaffolding for upcoming lessons unusually often (see the `getConventionSamples`/`FEATURE_MODELS` entries above, and `client/insights.md`'s `conventions.json` entry), so "doesn't show up in the files I've read so far" is not the same as "doesn't exist."
- **2026-09-20** — `getFeatureModelOverride`'s doc comment (`server/src/modules/settings/feature-models.ts:30-34`) explicitly names `conventions` as an example of a caller that should use `getFeatureModelOverride` directly and keep its own dynamic default, NOT call `resolveFeatureModel` (that function is for callers with a static default, and would resolve conventions to the `FEATURE_MODELS` registry's `openai`/`gpt-5.4`, which also isn't a "cheap model"). Read a cited precedent file's own doc comments fully before deciding how to call it — the first draft of `server/specs/conventions-extractor.md` cited this exact file as precedent but then called the wrong one of its two exported functions.
- **2026-09-16** — A `reviews` row (and its `findings`) is only ever persisted on the success path of `ReviewRunExecutor.executeRuns`, right before `completeAgentRun(runId, {status:'done',...})`; a failed/cancelled run hits the `catch` block instead and never inserts a `reviews` row at all. So any query that joins through `reviews` is already implicitly scoped to completed runs — no need to additionally join/filter on `agent_runs.status` (`server/src/modules/reviews/run-executor.ts:218-254,292-310`).
- **2026-09-20** — `fflate`'s `unzipSync(data, { filter })` calls the filter callback with just central-directory metadata (`name`, `size`, `originalSize`, `compression`) BEFORE deciding whether to inflate an entry — returning `false` guarantees that entry's bytes are never decompressed. Used in `server/src/modules/skills/import-parser.ts` to guarantee a zip's non-`.md`/`.txt` entries (scripts, binaries) are never read past their name/size, and to enforce a decompressed-byte-total cap (zip-bomb guard) and a total-entry-count cap purely from data the filter already receives, with no separate archive-walking pass needed.
- **2026-09-21** — A hostname blocklist for SSRF protection (`server/src/modules/skills/url-import.ts`, `server/specs/skill-url-import.md`) must NOT use a prefix regex like `/^10\./` against the raw hostname — it also matches the perfectly ordinary domain `10.example.com`, which is not an IP literal at all. Caught by this file's own test suite (`server/test/skill-url-import.test.ts`) during implementation, not by review. Fix: parse the hostname as four numeric dot-separated octets FIRST (`ipv4Octets()`), and only range-check the parsed octets — a domain name that merely starts with digits then fails that parse and is never blocked. Related gotcha hit in the same file: `new URL(u).hostname` for an IPv6 literal KEEPS the brackets (`"[::1]"`, not `"::1"`) — confirmed empirically (`node -e "console.log(new URL('https://[::1]/').hostname)"`), don't assume they're stripped.
